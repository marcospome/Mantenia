Empieza desde cero con JavaScript, TypeScript, Vite y React, y después explica todo lo que pasa entre que el usuario toca un botón en React y el método de C# responde: el proxy, la función que hace los pedidos, el token, el contrato de datos, la caché y los errores. 02JavaScript desde cero (1): variables, funciones, objetos y listas

JavaScript (JS) es el único lenguaje que los navegadores entienden directamente. Se parece bastante a C# en la forma de escribir (llaves, punto y coma, if), pero tiene diferencias importantes.

Variables: const y let

1 const nombre = "Compresor C-02";
2 let cantidad = 2;
  cantidad = 3;                 // se puede cambiar
3 nombre = "Otro";              // ERROR: const no se puede reasignar
  1. const: una caja que no se vuelve a asignar. Es lo que más se usa.
  2. let: una caja que se puede cambiar.
  3. A diferencia de C#, no se escribe el tipo: JavaScript lo averigua al ejecutar. (TypeScript, que vemos después, agrega los tipos).

En JavaScript las funciones son valores: se pueden guardar en variables y pasar como datos a otras funciones. Por eso vas a ver cosas como onClick={() => cambiarFiltro("riesgo")}: le estamos pasando una función al botón para que la ejecute cuando lo toquen.

Un objeto es un grupo de pares nombre: valor entre llaves. Es exactamente la forma del JSON que manda la API: por eso la app lo usa directamente.

Arrays (listas) y sus métodos

const activos = [ { nombre: "C-02", nivel: "riesgo" }, { nombre: "B-11", nivel: "ok" } ];

activos.length                                   // 2
activos[0].nombre                                // "C-02" (empieza en 0)
1 activos.filter((a) => a.nivel === "riesgo")       // [ { nombre: "C-02", … } ]
2 activos.map((a) => a.nombre)                      // [ "C-02", "B-11" ]
3 activos.find((a) => a.nombre === "B-11")         // { nombre: "B-11", … }
4 activos.some((a) => a.nivel === "riesgo")         // true
  1. filter = Where de LINQ: deja los que cumplen.
  2. map = Select de LINQ: transforma cada uno. En React se usa todo el tiempo para convertir una lista de datos en una lista de filas en pantalla.
  3. find = FirstOrDefault: el primero que cumple, o undefined.
  4. some = Any: ¿alguno cumple?

=== en vez de ==: en JavaScript se compara con tres iguales. == hace conversiones raras ("5" == 5 da true). Con ===, "5" === 5 da false, como esperarías.

En la consola: [1, 2, 3].map(x => x * 10) → [10, 20, 30]. Después [1, 2, 3].filter(x => x > 1) → [2, 3].

  • const (no cambia) y let (cambia). No se escribe el tipo.
  • Funciones flecha: (a) => a * 2.
  • Objetos { clave: valor } = la forma del JSON. Arrays [ ] con map, filter, find.

Ejemplo real con varios símbolos juntos

const set = (clave, valor) => setForm((f) => ({ ...f, [clave]: valor }));

Se lee de afuera hacia adentro: set es una función que recibe una clave (por ejemplo "nombre") y un valor. Llama a setForm con una función que recibe el formulario actual f y devuelve una copia (...f) con esa clave cambiada ([clave]: valor; los corchetes significan “usá el valor de la variable como nombre de la propiedad”). Promesas y async / await

Igual que en C#, ir a la API tarda. JavaScript no se queda congelado esperando: las operaciones lentas devuelven una Promise (promesa), que es el equivalente del Task de C#.

1 async function cargar() {
    try {
2   const res = await fetch("/api/app/activos");
3   const datos = await res.json();
      console.log(datos.total);
    } catch (e) {
4   console.log("falló", e);
    }
  }
  1. async marca que la función tiene esperas adentro (igual que en C#).
  2. fetch es la función del navegador para hacer pedidos HTTP. await espera la respuesta sin congelar la página.
  3. res.json() lee el cuerpo y lo convierte de texto JSON a objeto. También tarda, por eso lleva await.
  4. Si algo falla (sin red), salta al catch, como en C#.

JSON en JavaScript

JSON.stringify({ email: "ana@x.com" })     // objeto → texto: '{"email":"ana@x.com"}'  (para mandar)
JSON.parse('{"total":5}')                  // texto → objeto: { total: 5 }              (para leer)

Con esto ya se puede leer completa la función api() de la Parte 1: es un fetch con await, JSON.stringify para mandar, res.json() para leer y try/catch para los errores.

  • export ofrece algo; import lo usa desde otro archivo.
  • Promise = Task de C#. async/await/try/catch funcionan igual que en C#.
  • fetch hace el pedido; JSON.stringify y res.json() convierten entre objeto y texto.

05TypeScript: JavaScript con tipos

JavaScript no revisa tipos: si escribís activo.nombr (mal escrito), recién te enterás cuando la app falla en el navegador. TypeScript es JavaScript con tipos agregados, como en C#, para que el editor marque esos errores antes. Los archivos son .ts y, si tienen JSX, .tsx.

// Variables y parámetros con tipo

// Un tipo con opciones fijas
3 export type Perfil = "planta" | "taller";

// Genéricos, igual que en C#

  2. Una interface describe qué propiedades tiene un objeto. Es lo que usamos en types.ts para los datos de la API.
  3. Un type con | limita los valores posibles: Perfil solo puede ser “planta” o “taller”. Si escribís “tallr”, el editor lo marca.
  4. Los genéricos <T> funcionan como en C#.
  5. as le dice al compilador qué tipo es algo que él no puede saber (lo que viene del JSON).

Importante: los tipos de TypeScript desaparecen al traducir a JavaScript. Sirven para encontrar errores mientras escribimos, no existen cuando la app corre. Por eso types.ts no “controla” lo que manda la API: solo le dice al editor qué esperar.

  • TypeScript = JavaScript + tipos. Se escribe nombre: tipo.
  • interface describe la forma de un objeto; type con | limita valores.

07Vite, desde cero

Vite (se pronuncia “vit”, significa “rápido” en francés) es la herramienta que convierte nuestros archivos .tsx en una app que el navegador puede abrir. Tiene dos trabajos: servir la app mientras programamos y empaquetarla para publicarla.

¿Por qué hace falta?

  • El navegador no entiende TypeScript ni JSX: alguien tiene que traducirlos.
  • La app tiene decenas de archivos y librerías; para publicar conviene juntarlos en pocos archivos chicos.
  • Mientras programamos queremos ver los cambios al instante, sin recargar.
  • Necesitamos que /api llegue a la API (el proxy).

Trabajo 1 · Servidor de desarrollo (npm run dev)

Trabajo 2 · Empaquetar para publicar (npm run build)

vite.config.ts completo

1 import { defineConfig, loadEnv } from "vite";
  import react from "@vitejs/plugin-react";
  import tailwindcss from "@tailwindcss/vite";
  import basicSsl from "@vitejs/plugin-basic-ssl";

2 export default defineConfig(({ mode }) => {
3 const env = loadEnv(mode, process.cwd(), "");
    return {
4   plugins: [react(), tailwindcss(), ...(mode === "https" ? [basicSsl()] : [])],
      server: {
5     host: true,
        port: 5173,
6     proxy: { "/api": { target: env.VITE_API_PROXY || "http://localhost:5080", changeOrigin: true } },
      },
    };
  });
  1. Importa Vite y tres plugins (agregados): uno para React (entiende JSX), uno para Tailwind (genera el CSS) y uno para HTTPS local.
  2. Exporta la configuración. Es una función que recibe el modo: development por defecto, o https si se usó npm run dev:https.
  3. Lee los archivos .env (variables de configuración).
  4. Activa los plugins. El de HTTPS solo si el modo es https: ...(condición ? [x] : []) agrega x a la lista solo si se cumple.
  5. host: true permite abrir la app desde el celular en la misma red Wi-Fi, con la IP de la PC.
  6. El proxy: lo que empiece con /api se reenvía a la API.

Variables de entorno (.env)

Un archivo .env guarda configuración fuera del código, en líneas NOMBRE=valor. Vite solo deja que la app lea las que empiezan con VITE_, a través de import.meta.env:

# mantenia-app/.env (se copia desde .env.example)
VITE_API_PROXY=http://localhost:5080
VITE_API_URL=

// src/api/client.ts
const BASE_URL = import.meta.env.VITE_API_URL ?? "";

Ojo: el valor se “pega” en el código al compilar. Si cambiás VITE_API_URL, hay que volver a hacer npm run build.

  • Vite traduce TSX a JavaScript, sirve la app en localhost:5173, recarga sola al guardar y hace de proxy hacia la API.
  • npm run build genera dist/, que es lo que se publica.
  • Configuración en vite.config.ts y variables VITE_… en .env.

08React desde cero (1): componentes, JSX y props

React es una librería para armar pantallas a partir de piezas llamadas componentes. Un componente es una función de JavaScript que devuelve lo que hay que dibujar.

src/components/ui.tsx (el chip de los filtros, con los estilos resumidos) 
1 export function Chip({ activo, children, onClick }: { activo: boolean; children: ReactNode; onClick: () => void }) {
2 return (
3   <button
        type="button"
4     onClick={onClick}
5     className={cx("rounded-full border px-4 py-2", activo ? "bg-ink text-white" : "bg-white text-ink")}

6     {children}

7 <Chip activo={filtro === "riesgo"} onClick={() => cambiarFiltro("riesgo")}>

  1. Un componente se llama con mayúscula. Recibe un objeto con sus datos (las props), que acá se desestructura: activo, children y onClick. Después de los dos puntos está el tipo de TypeScript de esas props.
  2. Devuelve lo que hay que dibujar.
  3. JSX: se ve como HTML pero está dentro de JavaScript. React lo convierte en elementos reales de la página.
  4. Las llaves { } dentro del JSX significan “acá va JavaScript”. Acá le pasamos al botón la función a ejecutar cuando lo tocan.
  5. className (no class, porque class es palabra reservada de JS) lleva los estilos. cx es una función nuestra que junta las clases y descarta las vacías. Si está activo, fondo oscuro; si no, blanco.
  6. children es lo que se escribe entre la etiqueta de apertura y la de cierre al usarlo (“En riesgo 1”).
  7. Usarlo es escribir <Chip …> como si fuera una etiqueta HTML, pasando las props como atributos.

09React desde cero (2): estado, eventos y efectos

Estado: useState

El estado es la memoria de un componente: datos que cambian mientras se usa la pantalla (lo que se escribe, el filtro elegido). Cuando el estado cambia, React vuelve a dibujar el componente.

1 const [texto, setTexto] = useState("");

  <input
2   value={texto}
3   onChange={(e) => setTexto(e.target.value)}
  />

34Preguntas probables sobre la conexión

¿Cómo se comunica la app con la API?

Por HTTP con JSON. Todas las llamadas pasan por la función api() de client.ts, que agrega el token en el header Authorization: Bearer y convierte las respuestas y los errores.

¿Cómo sabe la app dónde está la API?

En desarrollo usa rutas relativas (/api/...) y el proxy de Vite las reenvía a localhost:5080. En producción se define VITE_API_URL, o se publica todo en el mismo dominio.

¿Qué es el proxy de Vite y por qué lo usan?

Una función del servidor de desarrollo que reenvía los pedidos a /api hacia la API. Para el navegador todo viene del mismo origen, así que no aparece el bloqueo de CORS.

¿Qué es CORS?

Una protección de los navegadores: una página solo puede leer respuestas de otro origen si ese servidor lo autoriza. La API autoriza los orígenes de Cors:Origenes.

¿Dónde guardan el token y por qué ahí?

En localStorage, con su vencimiento, para que la sesión sobreviva a cerrar la pestaña. Se revisa el vencimiento antes de usarlo.

¿Qué pasa si el token vence en medio del uso?

La API responde 401; api() borra la sesión y llama a salir, y la app vuelve al login recordando qué pantalla se quería abrir.

¿Cómo se asegura que la app y la API usen los mismos campos?

Los DTOs de C# y las interfaces de types.ts se escriben con los mismos campos. .NET convierte los nombres a camelCase. Si se cambia uno, hay que cambiar el otro a mano.

¿Qué es TanStack Query y para qué lo usan?

Una librería para pedir datos: maneja la caché, los estados de carga y error, los reintentos y la actualización automática. Cada endpoint de lectura tiene un hook useQuery; cada escritura un useMutation.

¿Qué es la caché y cuánto dura?

Las respuestas quedan guardadas en memoria con una clave (queryKey). Se consideran frescas 30 segundos; después se muestran igual y se actualizan en segundo plano.

¿Por qué después de guardar se actualizan todas las pantallas?

Porque onSuccess invalida las claves de la caché relacionadas (activos, dashboard, órdenes, reportes, catálogos) y TanStack Query las vuelve a pedir.

¿Por qué el buscador no llama a la API en cada tecla?

Por el debounce de 300 ms: solo busca cuando el usuario deja de escribir. Además, si llega una búsqueda nueva, la anterior se cancela.

¿Cómo muestran los errores de validación de la API?

leerError lee errors del ProblemDetails y lo guarda en el ApiError; el formulario busca el error de cada campo con errorDe y lo muestra debajo del input.

¿Por qué no reintentan los errores 4xx?

Porque no se arreglan solos: datos inválidos, sin permiso o inexistente. Solo se reintentan errores de red o del servidor, hasta 2 veces.

¿Cómo se esconden los botones según el permiso?

El contexto trae la lista de permisos del rol; puede("clave") dice si está. Es solo visual: la API controla igual.

¿Qué diferencia hay entre useQuery y useMutation?

useQuery lee y se ejecuta sola al mostrarse la pantalla; useMutation escribe y se ejecuta cuando el usuario hace algo (guardar, borrar).

¿Cómo cancelan un pedido si el usuario se va de la pantalla?

TanStack Query le pasa a queryFn una señal (signal) que se reenvía a fetch. Si la pantalla se desmonta o cambia la búsqueda, se aborta.
